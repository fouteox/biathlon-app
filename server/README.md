# Biathlon server

Cloudflare Worker that:

- polls biathlonresults.com every minute (Cron Trigger) during World Cup events and detects cancelled races and start time changes;
- sends the matching alerts through APNs to registered devices (texts are localized on the device, see `src/payload.ts`);
- runs one Live Activity per race (`src/live.ts`), each in a Durable Object of its own named after the race (`RaceActivity`, `src/raceActivity.ts`): the object opens an APNs broadcast channel per environment for the upcoming race, publishes each new state (start time, phase, first three) on it while the race runs, then ends the activity, sends the end again every 10 minutes for an hour for devices that were offline (the channels store no messages), and deletes the channel at APNs, from its alarm once the cron no longer needs to call it;
- exposes a read-only cache of the IBU API under `/ibu/`, which the app reads instead of biathlonresults.com. The Cache API also works on `*.workers.dev` (`cf-cache-status: HIT`, measured on 2026-10-19).

### App Attest

Device registrations must come from the app on a genuine Apple device ([App Attest](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server)). At its first sync, the app generates a key, attests it with the SHA-256 of a challenge as `clientDataHash`, and posts the attestation to `/v1/app-attest/keys`. The server checks it against Apple's App Attestation Root CA and the `APP_ATTEST_APP_ID` secret (App ID prefix, a period, the bundle ID), and verifies the receipt that comes with it ([signature up to Apple Root CA - G3, App ID, created within five minutes, same public key](https://developer.apple.com/documentation/devicecheck/assessing-fraud-risk#Verify-the-receipt)), then stores the public key and the receipt. The objects are CBOR, decoded with [cborg](https://github.com/rvagg/cborg), and the certificates are read and checked with [@peculiar/x509](https://github.com/PeculiarVentures/x509) on WebCrypto, which needs the `reflect-metadata` polyfill. Challenges are stateless, signed with the `APP_ATTEST_SECRET` secret: replays are stopped by the one attestation per key and the assertion counter. Keys no device has used for 30 days are deleted once a day. Attestations and assertions from builds older than the `APP_ATTEST_MIN_BUNDLE_VERSION` variable (a `CFBundleVersion`) are rejected: raise it in `wrangler.jsonc` and deploy to shut out the builds before a fix.

Each `PUT` and `DELETE` on `/v1/devices/:token` and `/v1/live-activity-starts/:token` then carries three headers: `X-App-Attest-Key-Id`, `X-App-Attest-Challenge` (a fresh challenge) and `X-App-Attest-Assertion`, an assertion whose `clientData` is the UTF-8 bytes of `"<challenge>\n<METHOD> <path>\n"` followed by the raw request body. A `401` with `{"error":"unknown key"}` tells the app to attest a new key. Each key holds one token of each kind, and only that key can change or delete it (`403` otherwise): the token changes on reinstall, restore and migration, like the key.

## Deploy

1. In the Apple Developer account (Certificates, Identifiers & Profiles > Keys), create two team-scoped APNs keys, one for Sandbox and one for Production, as Apple recommends one key per environment. Note each Key ID and the Team ID (Membership details).
   In Identifiers, open `com.fouteox.biathlon` and check **Broadcast Capability** under Push Notifications: Live Activity channels need it, and Xcode can't enable it.
2. From this folder:

   ```sh
   npm ci
   npx wrangler login
   npx wrangler d1 create biathlon          # paste the printed database_id into wrangler.jsonc
   npx wrangler secret put APNS_TEAM_ID
   npx wrangler secret put APP_ATTEST_APP_ID   # <App ID prefix>.com.fouteox.biathlon, from Identifiers
   openssl rand -base64 32 | npx wrangler secret put APP_ATTEST_SECRET
   npx wrangler secret put APNS_SANDBOX_KEY_ID
   npx wrangler secret put APNS_SANDBOX_KEY < AuthKey_SANDBOXKEYID.p8
   npx wrangler secret put APNS_PRODUCTION_KEY_ID
   npx wrangler secret put APNS_PRODUCTION_KEY < AuthKey_PRODKEYID.p8
   npm run deploy                           # applies the pending D1 migrations, then deploys
   curl https://biathlon-server.<subdomain>.workers.dev/v1/health
   ```

3. Every later deploy is automatic: each push to `main` that changes `server/` runs the `Deploy server` workflow (`.github/workflows/deploy-server.yml`), which runs the checks on that commit, then `npm run deploy`, then checks `/v1/health`. It reads two secrets of the `production` environment of the GitHub repository (Settings > Environments), whose deployment branches are limited to `main`:
   - `CLOUDFLARE_ACCOUNT_ID`: the account ID (Workers & Pages > Account details);
   - `CLOUDFLARE_API_TOKEN`: an account API token (Manage account > Account API tokens > Create Token) from the **Edit Cloudflare Workers** template, with **Account > D1 > Edit** added and scoped to this account only.

   Migrations are applied before the new code is deployed, so the version still running meets the new schema for a few seconds: a migration must keep working with the code already deployed (add columns with a default, rebuild a table with the same columns plus new ones), and a column is dropped only once no deployed code reads it.

## Limits (Workers Free plan)

Each request to APNs or to the IBU API is a subrequest, and the Free plan allows 50 per invocation (requests to Cloudflare services such as D1 and Durable Objects count separately, up to 1,000). Each Durable Object invocation has its own 50, so device pushes (alerts and Live Activity starts) go out in lots of 50, each sent by a `PushSender` Durable Object (`src/pushSender.ts`, `src/pushLots.ts`), 6 at a time, the connections a Durable Object request may wait on at once: measured on the Free plan, one run made 45 subrequests itself and 4 × 50 through Durable Objects. Concurrent requests to one Durable Object share its 50, so each lot goes to a new object (`newUniqueId`). Cloudflare sometimes fires the cron twice for one minute (3 times in a day, measured on 2026-10-25): a run skips a minute already started (`claimCronRun`, the `cron_minute` setting), which would otherwise send the same alerts twice. A run sends at most 500 alerts, and each race's update at most 500 Live Activity starts (`MAX_PUSHES_PER_RUN`); the rest wait for the next runs, in the `outbox` table for alerts, which are dropped after 30 minutes. Each lot is one of the Free plan's 100,000 Durable Object requests a day. D1 allows 50 queries per invocation on the Free plan, a `db.batch()` counting as one whatever its statements ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)): pushes are claimed and settled in a few batches of set-based statements (`json_each`), so their number doesn't count. On the Paid plan, raise `SUBREQUESTS_PER_RUN` and `MAX_PUSHES_PER_RUN`.

The run's own subrequests go to the IBU calendar, then each race the calendar lists goes, all at once, to its `RaceActivity` Durable Object, `getByName(raceId)`: one request per race and minute, some 10,000 a day during an event, with the run's provider tokens, as objects signing their own at once would renew them more often than the 20 minutes APNs accepts. Each object invocation has its own 50 subrequests, so a race never waits for another's: per update, at most one IBU request, shared by the leaders and the start list, one channel creation and one broadcast per environment, and the start pushes of the favorites, in lots. An object runs one update at a time (`blockConcurrencyWhile`), so overlapping cron runs never interleave on a race, and skips a run older than the last change it recorded. The object is reset once an update has run 30 seconds, and a subrequest has no time limit of its own: an update gives up its APNs and IBU requests still unanswered after 20 seconds, its lots' pushes included, for a later update. Measured with every request answered in 100 ms, an update takes some 0.3 s, and 2.4 s with 500 start pushes whose provider token APNs rejects. Its alarm sends the ends again and deletes the channels at APNs, retries what failed a minute later, and ends the activity of a race the calendar stopped listing 12 hours after its start, the longest an activity stays on screen. The channels stay in D1 (`live_channels`), written only by the race's object, for the app's `GET` of a channel: those reads would otherwise spend the Durable Object requests.

The anonymous routes, `/v1/app-attest/challenges` and the IBU requests the cache can't answer, are rate limited per client IP address with the [Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) (`ratelimits` in `wrangler.jsonc`), which counts in each Cloudflare location and only approximately. Cloudflare advises against keying on the address, which many users can share, but these requests carry nothing else: hence limits far above what one app sends, 30 challenges and 60 IBU requests a minute. They spare the IBU API and the Worker's CPU time, not the Worker's daily requests.

Once a day, at 03:00 UTC, the cron deletes the data nothing reads any more: Live Activity starts of races started over two days ago, favorites not sent for a year, App Attest keys unused for 30 days, channels deleted at APNs whose activity ended over 12 hours ago (the longest an activity stays on screen, until then the app learns it ended), and the races of past seasons.

## Develop

```sh
npm ci
npm run check        # as in CI: generated types, format, lint, type check (vp check), tests
npx vp check --fix   # format and apply the lint fixes
npx vp test          # the tests alone; `npx vp test watch` reruns them on each change
npx wrangler d1 migrations apply biathlon --local
cp .dev.vars.example .dev.vars   # fill in a key
npx wrangler dev
curl "http://localhost:8787/cdn-cgi/local/scheduled?format=json"
```

Run `npx wrangler types` after editing `wrangler.jsonc`.

The tests run in workerd, the Workers runtime, with [`@cloudflare/vitest-plugin`](https://developers.cloudflare.com/workers/testing/vitest-integration/) (`vite.config.ts`): the bindings of `wrangler.jsonc` with test values for its secrets, a local D1 database emptied and migrated with `migrations/*.sql` before each test (`test/setup.ts`), the `PushSender` Durable Object and the Cache API. Requests to APNs and the IBU API never reach the network: each test answers them with [MSW](https://developers.cloudflare.com/workers/testing/vitest-integration/mock-outbound-requests/) (`test/network.ts`), and an unanswered request fails the test. The full suite takes about 10 seconds.
